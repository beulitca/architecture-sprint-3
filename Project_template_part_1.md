### 2. Анализ архитектуры монолитного приложения

Язык программирования: Java
База данных: PostgreSQL
Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
Взаимодействие: Синхронное, запросы обрабатываются последовательно.
Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
Развёртывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Домены:
1. Домен адаптер устройствами - реализует взаимодействие с устройствами, инкапсулирует технические особенности интеграции с оборудованием
2. Домен управления пользователями - CRUD-справочник лиц, имеющих доступ к системе.
3. Домен уведомлений - рассылка сообщений клиентам и сотрудникам компании по событиям системы, поддерживает разные протоколы.
4. Домен авторизации/аутентификации - поддерживает различные сценарии авторизации/аутентиикации, управлет правами доступа к ресурсам
5. Домен умного дома - оркестриует сценарии работы с умным домом, BFF web-сайта, обращается к устройствам через Домен управления устройствами
6. Домен устройств - управляет реестром устройств, зарегистрированных а каждом доме системы


### **4. Проблемы монолитного решения**
В теории было приведено огромное количество выкладок по плюсам и минусам тех или иных решений, отолкнемся от 12 факторов:
Тема 2.4 - У 1.9 
- Сильная связность частей системы 
    => влияние ошибки на весь функцинал
    => сложность обновления отдельных частей
    => сложность масштабирования отдельных частей
    => сложность согласования изменений с командой, нет разделения специалистов по работе с устройствами и разработчиков 
  => Длительный цикл разработки, потери в надежности и отказоустойчивости

Ввиду масштабов текущего приложения монолитное решение могло бы подойти, если бы не наличие в команде специалистов разной направленности: по устройствам и разработчиков, границы компетенций которых нет смысла размывать. Также управление домом является критическим функционалом и требует обеспечения надежности, отказоустойчивости и возможности быстрых обновлений отдельных частей. Учитывая планирующийся рост нагрузки и расширения функционала, переход на микросервисную архитектуру обоснован.
